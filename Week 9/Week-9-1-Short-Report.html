WEEK 09_1 · SHORT REPORT

Web Accessibility & Lighthouse Audit.

This short report summarizes the Week 9_1 lesson on making web pages easier to use for people with different abilities, including people who navigate with a keyboard or use screen readers.

1. Aim of the activity

The aim was to understand basic web accessibility principles and use Google Lighthouse to review a web page. An accessibility audit helps identify barriers in page structure, text alternatives, navigation, form controls, and visual presentation.

2. Method

  1. Open the project page in Google Chrome and launch Developer Tools.
  2. Select Lighthouse, choose the Accessibility category, and run an audit.
  3. Review the audit recommendations and inspect the relevant HTML and CSS.
  4. Improve the page using semantic elements, accessible names, keyboard-friendly controls, and readable contrast where needed.
  5. Run the audit again and compare the new result with the initial test.

The before, issue, and after screenshots are available in the Week 9 accessibility evidence gallery.

3. Main concepts learned

  • Semantic HTML: use meaningful elements such as header, nav, main, section, and footer so assistive technologies can understand the page structure.
  • Keyboard navigation: interactive elements should work with a keyboard. Native button and a elements are preferable to clickable generic div elements.
  • Alternative text: meaningful images need concise alt descriptions; decorative images should not create unnecessary announcements.
  • ARIA attributes: use labels and live-region attributes when native HTML alone does not provide enough accessible information. ARIA should support semantic HTML, not replace it.
  • Color contrast and focus: text should be readable, and keyboard users should be able to see which element currently has focus.

4. Connection to Week 8_2: JavaScript form validation

Week 8_2 covered client-side form validation. Accessibility is also important in forms: every input needs a clear label, validation errors should explain how to correct the problem, and dynamic feedback should be announced to assistive technology when appropriate. For example, an aria-live message can announce a validation result without forcing the user to search the page for it.

The main lesson is that a form should not only reject invalid data; it should clearly help the user understand and correct the error.

6. Conclusion

This activity showed me that accessibility should be considered while building a website, not added only at the end. Semantic HTML, keyboard support, useful alternative text, clear form feedback, and sufficient contrast make a website more inclusive and easier for everyone to use. Lighthouse is useful for finding possible problems, but manual keyboard and screen-reader checks are also important.
