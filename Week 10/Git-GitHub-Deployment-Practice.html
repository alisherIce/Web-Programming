WEEK 10 · PRACTICE NOTES

Git, GitHub & Deployment.

A practical guide to the Week 10 workflow: track changes with Git, work safely with branches, collaborate through pull requests, publish a website with GitHub Pages, and create a helpful custom 404 page. The commands below are learning examples—run them in your own project and record your actual results.

1. Create a Git repository and make your first commit

Git records snapshots of your project. A commit is a named checkpoint that lets you review changes and return to earlier versions.

mkdir my-first-git
cd my-first-git
git init
echo "<h1>Hello Git</h1>" > index.html
git status
git add index.html
git commit -m "Initial commit: add index.html"
git log --oneline

What to understand: git init creates the local repository, git status shows changed and untracked files, git add stages selected changes, and git commit saves a checkpoint.

2. Create a branch, make a change, and merge it

Branches let you work on a feature without changing the main version until the work is ready.

git switch -c feature-style
# Make a change, for example create style.css
git add style.css
git commit -m "Add basic stylesheet"
git switch main
git merge feature-style
git log --oneline --graph --all

Key idea: merging brings the branch's changes into main. Review the graph and confirm that the expected files are present.

3. Connect the local repository to GitHub

Create an empty repository on GitHub, then connect it as the remote named origin.

git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git
git remote -v
git push -u origin main

For later updates, the usual sequence is:

git status
git add .
git commit -m "Describe the change"
git push

Replace the placeholder URL with your own repository URL. Do not copy another student's remote URL or commit hashes.

4. Collaborate with a pull request

  1. Create a feature branch, for example add-readme.
  2. Make a focused change and commit it with a clear message.
  3. Push the branch to GitHub.
  4. Open a pull request from the feature branch into main.
  5. Review the changed files and description, then merge when ready.
  6. Switch back to main and pull the merged changes.
git switch -c add-readme
# Create or edit README.md
git add README.md
git commit -m "Add README"
git push -u origin add-readme
# Open and review the pull request on GitHub
git switch main
git pull origin main

A pull request is a review-and-merge workflow. It is useful even for individual projects because it makes changes easier to inspect before merging.

5. Publish a website with GitHub Pages

  1. Make sure the repository contains an index.html entry page.
  2. Push the website files to GitHub.
  3. Open the repository's Settings → Pages.
  4. Choose Deploy from a branch, select main and the correct folder (usually /(root)), then save.
  5. Wait for the deployment to finish and open the published URL.
  6. Test navigation, images, CSS, and links on the live site—not only on your computer.

6. Understand and create a custom 404 page

A 404 page appears when a visitor opens a URL that does not exist. A useful page explains the problem and provides a clear route back to the site.

For a GitHub Pages site, add a file named 404.html in the published folder. A simple starting point:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Page Not Found</title>
</head>
<body>
  <main>
    <h1>404 — Page not found</h1>
    <p>Sorry, this page does not exist.</p>
    <a href="./">Back to home</a>
  </main>
</body>
</html>

After publishing, test a deliberately incorrect URL and confirm that your custom page appears. Keep its design consistent with the rest of your portfolio.
